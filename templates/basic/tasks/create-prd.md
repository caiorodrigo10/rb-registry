# PRD Generation Guidelines

This document provides guidelines for creating high-quality Product Requirements Documents (PRDs).

## PRD Structure

A well-structured PRD should include the following sections:

### 1. Project Overview
- **Project Name**: Clear, descriptive name
- **Project Description**: 2-3 sentences explaining what the project is
- **Project Type**: Frontend, Backend, Fullstack, Mobile, Desktop, or Utility
- **Target Users**: Who will use this project

### 2. Goals & Objectives
List 4-6 specific goals that this project aims to achieve:
- Each goal should be measurable
- Focus on user value and business impact
- Prioritize by importance (if applicable)

### 3. User Stories
Provide 3-5 user stories in the format:
```
As a [type of user],
I want to [perform some action],
So that I can [achieve some goal/benefit].
```

### 4. Functional Requirements

#### Core Features
List 5-10 core features that are essential to the project:
- Feature name and brief description
- Priority level (High/Medium/Low)
- Estimated complexity (if known)

#### Out of Scope
Explicitly list features that are NOT included in this version

### 5. Success Metrics
Define 3-5 specific, measurable metrics:
- How will you measure success?
- What are the target numbers?
- How will these be tracked?

### 6. Technical Considerations
- **Recommended Stack**: Technologies and frameworks
- **Architecture**: High-level architecture decisions
- **Dependencies**: External libraries or services
- **Constraints**: Technical limitations or requirements
- **Security**: Security considerations
- **Performance**: Performance requirements

### 7. Timeline & Milestones
- **Estimated Timeline**: Overall project duration
- **Key Milestones**: Major checkpoints
- **Delivery Phases**: If applicable

### 8. Implementation Notes
- Development approach
- Testing strategy
- Documentation requirements
- Deployment considerations

## Quality Standards

A good PRD should be:
- **Clear**: Easy to understand for all stakeholders
- **Concise**: Focused and to-the-point
- **Complete**: Covers all necessary aspects
- **Consistent**: Uses consistent terminology
- **Actionable**: Can be translated into tasks

## Tone & Style

- Use clear, professional language
- Be specific and avoid vague terms
- Focus on "what" and "why", not "how"
- Use bullet points for readability
- Include examples when helpful
